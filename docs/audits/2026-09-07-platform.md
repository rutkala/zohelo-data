## Goal coverage and open decisions

- **NBP source coverage:** all four configured source IDs have state, source metadata, and model metadata. The historical probe above validates representative ranges only; gaps, recheck latency, and old missing legacy history remain unresolved.
- **Metrics:** the catalogue deliberately has no business metrics. Metric use cases, definitions, dimensions, time aggregation, and approval remain owner decisions; the synthetic native MetricFlow fixture must not be presented as production coverage.
- **New sources:** no source expansion is approved. Commercial reuse, attribution, and licensing evidence must be reviewed before onboarding another source; public HTTP access alone is insufficient.
- **UI:** catalogue discovery is implemented alongside SQL, while a redesigned portal and served backend remain deferred decisions.

## Cost, risk, and release status

The runner bounds an invocation to 2,048 observation batches, 512 requests, 256 MiB working raw data, 12 MB per response, and 45 minutes of intake. The state/raw inventory can grow by roughly 8 observation batches per day; long-term growth requires compaction and retention work before these bounds are reached. No new paid service is assumed. Actual runner usage, peak RAM, and query p95 still require live proof. The existing 5 TB Drive allocation does not imply unlimited compute.

The current live release is v1 silver. The feature branch is implementation evidence only; it is not a full release, and no v2 live status is claimed until the release is explicitly confirmed. The remaining acceptance evidence is a fresh-process restore/query, native cold replay, browser fixture check, and a rechecked Python suite. Business metric approval, new-source commercial licensing, and served-backend availability remain open.
