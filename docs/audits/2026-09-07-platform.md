## Goal coverage and open decisions

- **NBP source coverage:** all four sources have verified request coverage through 6 September 2026. The new silver release retains every prior key and recovers 184 additional historical records. This does not reconstruct missing original legacy raw versions or establish immediate detection of all future source revisions.
- **Metrics:** the catalogue deliberately has no business metrics. Metric use cases, definitions, dimensions, time aggregation, and approval remain owner decisions; the synthetic native MetricFlow fixture must not be presented as production coverage.
- **New sources:** no source expansion is approved. Commercial reuse, attribution, and licensing evidence must be reviewed before onboarding another source; public HTTP access alone is insufficient.
- **UI:** catalogue discovery is implemented alongside SQL; a redesigned portal and served backend remain deferred.

## Cost, risk, and release status

The runner bounds one invocation to 2,048 observation batches total across the four sources plus catch-up, 512 requests, 256 MiB working raw data, 12 MB per response, and 60 minutes of intake. The state/raw inventory can grow by roughly eight observation batches per day; long-term growth requires compaction before these bounds are reached. GitHub documents standard Actions runner minutes as free for public repositories in its [product billing guidance](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Drive service limits are documented in the [Drive API quota policy](https://developers.google.com/workspace/drive/api/guides/limits). Account-specific quotas and billing were not inspected, and no free-unlimited promise is made. The successful resumed bootstrap took 66 min 37 sec, including 58 min 12 sec of intake, with 75,267,018 bytes in its working directory and 10,077,163 bytes of published Parquet. Peak RAM, representative query p95, account-specific quotas and total billing remain unmeasured; existing 5 TB storage does not provide unlimited compute.

The current verified Drive snapshot is v2 release `5f356b1b-97cd-470d-9d5e-b46ebb37a7d1`. The measured NBP data fits the present working-set bounds; the evidence supports keeping the current Drive/dbt/DuckDB architecture for this workload. The dominant measured cost is ingestion/transfer time. It does not justify a prediction for larger datasets or always-on metric serving. Business metric approval, new-source commercial licensing, and served-backend availability remain open.

## Bounded ingestion efficiency follow-up

The first bootstrap showed roughly 15 seconds between saved state snapshots. Code inspection found five repeated Drive operations immediately after each already-verified commit. The follow-up returns the exact verified pointer bytes and reuses the committed state in process. Every subsequent commit still reads the live pointer and checks for drift; immutable snapshot and pointer readback, ancestry checks, and size/hash checks remain. The 13 state tests and three runner tests passed locally, including reuse followed by competing-pointer rejection. Subsequent CI passed, including the once-per-invocation load regression. The successful run processed 226 requests in 3,492.142 intake seconds; no controlled before/after speedup was measured, so the saved-call change is not assigned a claimed percentage improvement.

## First live ingestion failure and repair

Run [34089760722](https://github.com/rutkala/zohelo-data/actions/runs/34089760722) retained 123 completed requests before rejecting an HTTP 200 Table B response containing the published `ZWR = 0.0` on 11 February 2009. The queued [resume run](https://github.com/rutkala/zohelo-data/actions/runs/34091184245) reused that progress and stopped on the same response. Neither published v2 data. The [source contract](../nbp-data-contracts.md#published-zero-fx-quotes-7-september-2026) records the repair and explicit zero-value flag.

The repaired runner prints safe validation reasons, stage transitions and a distinct checkpoint/budget status. Based on observed checkpoint latency, its intake budget is raised to 60 minutes within the unchanged 90-minute job, leaving 30 minutes for publication and recovery checks. This changes neither the total historical date scope nor the request/working-set bounds. The repaired run resumed that progress and passed all live data checks. The intake finished within its 60-minute budget; this was a resumed historical bootstrap, not a daily-run benchmark.

## Prioritized follow-ups

1. Agree the first business metric definitions, then implement and execute MetricFlow against the pinned gold release and expose the definitions and lineage in the catalogue. Runtime compatibility is already tested; production NBP semantic correctness is not.
2. Measure one routine incremental run, retained-state/raw growth, peak memory, and representative browser queries. The current 2,048-batch working limit and growing immutable state need a bounded compaction/selection strategy before they are reached.
3. Resolve historical FX unit normalization from provider evidence and review selected additional-source licences. Preserve values as published meanwhile; do not invent conversion rules or approval.

No new paid service was introduced by these changes. Billing and account-specific free allowances were not independently verified, so the audit does not certify an absolute zero-cost operating guarantee.
